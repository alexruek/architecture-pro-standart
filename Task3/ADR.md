# ADR-001: Архитектура онлайн-открытия депозитов и накопительных счетов

## Статус
Принято

## Дата
2026-03-09

## Контекст

Банк «Стандарт» реализует цифровую трансформацию депозитного направления. Сейчас клиенты могут открыть депозит или накопительный счёт только в отделении, что требует участия сотрудников фронт-офиса и бэк-офиса. Процесс занимает 20–60 минут.

Цель — реализовать MVP, при котором клиент может подать заявку на открытие депозита через интернет-банк и сайт. На этапе MVP заявку обрабатывают сотрудники бэк-офиса по старому процессу.

### Ключевые ограничения и требования
- База данных АБС перегружена; прямой онлайн-доступ интернет-банка к API АБС недопустим
- Интернет-банк — монолит ASP.NET MVC 4.5 / .NET Framework 4.5 / MS SQL на платформе подрядчика; ядро изменять нежелательно
- Функционал СМС-подтверждения должен быть реализован командой банка, без доработки ядра подрядчика
- Ставки по депозитам хранятся в XLS-файлах; нужно единое хранилище ставок, доступное бэк-офису депозитов и кредитов
- Доступность сервисов — 99,9% (24/7), с поддержкой резервного ЦОД и горизонтального масштабирования
- Данные клиентов при передаче должны быть защищены шифрованием (HTTPS/TLS)
- Данные при передаче с сайта — персональные, требуют защиты
- При необходимости очередей сообщений использовать Kafka (с учётом несовместимости текущей версии ИБ с Kafka)
- Рассмотреть микросервисную архитектуру для нового функционала в рамках задачи открытия депозитов

## Рассматриваемые решения

### Вариант 1 (отклонён): Прямая интеграция интернет-банка с АБС через существующий механизм (БД)
Интернет-банк напрямую пишет заявки в БД АБС.
- **Плюсы:** Простая реализация, нет новых компонентов.
- **Минусы:** БД АБС перегружена, прямой доступ может нарушить работоспособность банка. Интеграция через БД — антипаттерн. Не поддерживает 99,9% SLA с горизонтальным масштабированием.

### Вариант 2 (отклонён): Хранение ставок только в АБС с синхронным REST API
ИБ и сайт обращаются к АБС синхронно для получения ставок.
- **Плюсы:** Единый источник данных.
- **Минусы:** АБС не масштабируется горизонтально, высокая нагрузка, риск деградации основных банковских операций.

### Вариант 3 (принят): Новый микросервис депозитного домена с асинхронной интеграцией
Вводится новый **Сервис депозитных заявок** (Deposit Application Service), который принимает заявки от ИБ и сайта, хранит их и передаёт в АБС асинхронно. Ставки по депозитам хранятся в отдельном **Сервисе ставок** (Rate Service) с кэшированием на уровне приложения.

## Принятое решение

### Архитектурное решение

Для реализации MVP онлайн-открытия депозитов принято следующее решение:

1. **Создать новый Сервис депозитных заявок** (Deposit Application Service) — микросервис на Java Spring Boot. Сервис:
   - Принимает заявки от интернет-банка и сайта по REST API.
   - Сохраняет заявки в собственной БД PostgreSQL.
   - Передаёт заявки в АБС через очередь сообщений (Kafka) асинхронно.
   - Отправляет СМС-уведомления через СМС-шлюз.

2. **Создать Сервис ставок** (Rate Service) — микросервис на Java Spring Boot / PostgreSQL:
   - Хранит актуальные ставки по депозитным продуктам.
   - Предоставляет REST API для сайта и интернет-банка.
   - Кэширует ставки на уровне приложения.

3. **Интеграция интернет-банка**: команда банка реализует новые страницы и СМС-подтверждение в ИБ, взаимодействуя с новыми сервисами по REST.

4. **Инфраструктура**: развертывание Kafka для асинхронной связи с АБС. Горизонтальное масштабирование в двух ЦОД.

## C4 Диаграммы

### Уровень 1. Контекст системы (System Context)

```plantuml
@startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml

Person(client, "Клиент", "Физическое лицо, пользующееся услугами банка")
System(bank_standard, "Информационная система банка Стандарт", "Позволяет клиентам открывать депозиты и просматривать ставки")

System_Ext(sms_gateway, "СМС-шлюз", "Внешний шлюз для отправки СМС-сообщений")
System_Ext(telecom, "Телеком-оператор", "Внешний оператор связи")

Rel(client, bank_standard, "Пользуется сайтом и интернет-банком", "HTTPS")
Rel(bank_standard, sms_gateway, "Отправляет запросы на СМС", "REST API")
Rel(sms_gateway, telecom, "Передает сообщения")
Rel(telecom, client, "Доставляет СМС-коды и уведомления")
@enduml
```

### Уровень 2. Контейнеры (Containers)

```plantuml
@startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml

Person(client, "Клиент", "Пользователь банка")

System_Boundary(bank_boundary, "Банк Стандарт") {
    Container(website, "Сайт", "PHP, React", "Показывает ставки, принимает заявки")
    Container(ib, "Интернет-банк", "ASP.NET MVC 4.5", "Личный кабинет клиента")
    Container(deposit_service, "Deposit Application Service", "Java Spring Boot", "Управляет циклом заявок")
    Container(rate_service, "Rate Service", "Java Spring Boot", "Управляет ставками")
    ContainerDb(postgres, "PostgreSQL", "БД", "Хранение заявок и ставок")
    Container(abs, "АБС", "Oracle, Delphi", "Основная учетная система")
    Container(kafka, "Kafka", "Message Broker", "Асинхронная очередь сообщений")
}

System_Ext(sms_gateway, "СМС-шлюз", "Отправка СМС")

Rel(client, website, "Видит ставки, подает заявку", "HTTPS")
Rel(client, ib, "Видит персон. предложения, подает заявку", "HTTPS")

Rel(website, rate_service, "Запрашивает общие ставки", "REST API")
Rel(ib, rate_service, "Запрашивает персон. ставки", "REST API")

Rel(website, deposit_service, "Отправляет заявку", "REST API")
Rel(ib, deposit_service, "Отправляет заявку", "REST API")

Rel(deposit_service, postgres, "Сохраняет данные", "SQL")
Rel(rate_service, postgres, "Читает/пишет ставки", "SQL")

Rel(deposit_service, kafka, "Публикует заявку", "Produce")
Rel(abs, kafka, "Получает заявку", "Consume")

Rel(deposit_service, sms_gateway, "Запрос на СМС", "REST API")
@enduml
```

## Последствия

### Положительные
- АБС защищена от прямой онлайн-нагрузки через Kafka.
- Ставки хранятся в единой БД, доступной всем бэк-офисам.
- Архитектура поддерживает горизонтальное масштабирование и высокую доступность (99,9%).
- Минимизировано вмешательство в ядро интернет-банка (работы силами банка).

### Отрицательные / Риски
- Появление новых компонентов (Kafka, микросервисы) требует новых компетенций.
- Асинхронность вносит задержку в отображение статуса заявки.
- Необходимость реализации Consumer в АБС.
