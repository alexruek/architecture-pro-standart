# ADR-001: Архитектура онлайн-открытия депозитов и накопительных счетов

## Статус
Принято

## Дата
2026-03-07

## Контекст

Банк «Стандарт» реализует цифровую трансформацию депозитного направления. Сейчас клиенты могут открыть депозит или накопительный счёт только в отделении, что требует участия сотрудников фронт-офиса и бэк-офиса. Процесс занимает 20–60 минут.

Цель — реализовать MVP, при котором клиент может подать заявку на открытие депозита через интернет-банк и сайт. На этапе MVP заявку обрабатывают сотрудники бэк-офиса по старому процессу.

### Ключевые ограничения и требования
- База данных АБС перегружена; прямой онлайн-доступ интернет-банка к API АБС недопустим
- Интернет-банк — монолит ASP.NET MVC 4.5 / .NET Framework 4.5 / MS SQL на платформе подрядчика; ядро изменять нежелательно
- Функционал СМС-подтверждения должен быть реализован командой банка, без доработки ядра подрядчика
- Ставки по депозитам хранятся в XLS-файлах; нужно единое хранилище ставок, доступное бэк-офису депозитов и кредитов
- Доступность сервисов — 99,9% (24/7), с поддержкой резервного ЦОД и горизонтального масштабирования
- Данные клиентов при передаче должны быть защищены шифрованием (HTTPS/TLS)
- Данные при передаче с сайта — персональные, требуют защиты
- При необходимости очередей сообщений использовать Kafka (с учётом несовместимости текущей версии ИБ с Kafka)
- Рассмотреть микросервисную архитектуру для нового функционала в рамках задачи открытия депозитов

## Рассматриваемые решения

### Вариант 1 (отклонён): Прямая интеграция интернет-банка с АБС через существующий механизм (БД)
Интернет-банк напрямую пишет заявки в БД АБС.
- **Плюсы:** Простая реализация, нет новых компонентов.
- **Минусы:** БД АБС перегружена, прямой доступ может нарушить работоспособность банка. Интеграция через БД — антипаттерн. Не поддерживает 99,9% SLA с горизонтальным масштабированием.

### Вариант 2 (отклонён): Хранение ставок только в АБС с синхронным REST API
ИБ и сайт обращаются к АБС синхронно для получения ставок.
- **Плюсы:** Единый источник данных.
- **Минусы:** АБС не масштабируется горизонтально, высокая нагрузка, риск деградации основных банковских операций.

### Вариант 3 (принят): Новый микросервис депозитного домена с асинхронной интеграцией
Вводится новый **Сервис депозитных заявок** (Deposit Application Service), который принимает заявки от ИБ и сайта, хранит их и передаёт в АБС асинхронно. Ставки по депозитам хранятся в отдельном **Сервисе ставок** (Rate Service) с кэшированием на уровне приложения.

## Принятое решение

### Архитектурное решение

Для реализации MVP онлайн-открытия депозитов принято следующее решение:

1. **Создать новый Сервис депозитных заявок** (Deposit Application Service) — микросервис на Java Spring Boot (стек совместим с существующей платформой КЦ и экспертизой команды АБС). Сервис:
   - Принимает заявки от интернет-банка и сайта по REST API
   - Сохраняет заявки в собственной БД PostgreSQL
   - Передаёт заявки в АБС через очередь сообщений (Kafka) асинхронно — это изолирует АБС от онлайн-нагрузки
   - Отправляет СМС-уведомления через СМС-шлюз

2. **Создать Сервис ставок** (Rate Service) — лёгкий микросервис на Java Spring Boot / PostgreSQL:
   - Хранит актуальные ставки по депозитным продуктам
   - Предоставляет REST API для сайта и интернет-банка
   - Доступен для редактирования сотрудниками бэк-офиса (депозиты и кредиты) через простой UI или API
   - Кэширует ставки на уровне приложения (в памяти, TTL 5 мин) для снижения нагрузки

3. **Интеграция интернет-банка** — команда банка (без подрядчика) реализует новые модули в ИБ:
   - Страница списка депозитов со ставками из Rate Service
   - Форма подачи заявки
   - СМС-подтверждение заявки (реализуется как новый модуль командой банка, без изменения ядра подрядчика)

4. **Интеграция сайта** — команда сайта (PHP/React) добавляет:
   - Блок с актуальными ставками (Rate Service)
   - Форму заявки на депозит (передаёт в Deposit Application Service)

5. **Kafka** разворачивается как новый компонент инфраструктуры для асинхронной передачи заявок из Deposit Application Service в АБС. Интернет-банк (текущая версия) с Kafka не интегрируется напрямую — ИБ взаимодействует только с Deposit Application Service по REST.

6. **Горизонтальное масштабирование и HA**: Deposit Application Service и Rate Service разворачиваются в обоих ЦОД с балансировщиком нагрузки. АБС масштабируется только вертикально — новые сервисы буферизуют нагрузку.

## C4: Диаграмма контекста (уровень 1)

```
[Клиент] --> [Сайт банка] : подача заявки на депозит, просмотр ставок
[Клиент] --> [Интернет-банк] : подача заявки на депозит, просмотр ставок
[Сотрудник бэк-офиса] --> [АБС] : обработка заявок, управление ставками
[Сотрудник бэк-офиса] --> [Сервис ставок] : обновление ставок
[Клиент] <-- [СМС-шлюз / Телеком-оператор] : СМС-уведомления

[Сайт банка] --> [Deposit Application Service] : заявка на депозит
[Интернет-банк] --> [Deposit Application Service] : заявка на депозит
[Сайт банка] --> [Rate Service] : получение актуальных ставок
[Интернет-банк] --> [Rate Service] : получение актуальных ставок
[Deposit Application Service] --> [АБС] : передача заявок (через Kafka)
[Deposit Application Service] --> [СМС-шлюз] : отправка СМС
[АБС] --> [СМС-шлюз] : СМС-уведомление об открытии депозита
```

## C4: Диаграмма компонентов (уровень 3) — Deposit Application Service

```
[Deposit Application Service]
  ├── REST API Controller        : принимает запросы от ИБ и сайта
  ├── Application Service Layer  : бизнес-логика обработки заявок
  ├── Kafka Producer             : публикует заявки в топик deposit-applications
  ├── SMS Notification Client    : вызывает СМС-шлюз при изменении статуса заявки
  ├── Repository Layer           : работа с PostgreSQL
  └── PostgreSQL DB              : хранение заявок и их статусов

[АБС Kafka Consumer]           : читает заявки из топика deposit-applications, создаёт заявки в АБС
```

## Последствия

### Положительные
- АБС защищена от прямой онлайн-нагрузки: все заявки буферизуются через Kafka
- Ставки хранятся в едином месте, доступны бэк-офису депозитов и кредитов
- Горизонтальное масштабирование новых сервисов обеспечивает SLA 99,9%
- Ядро интернет-банка (подрядчик) не затрагивается
- Используются технологии, уже присутствующие в банке (Java Spring Boot, PostgreSQL)
- Заложена основа для перехода к полной автоматизации (целевое состояние через год)

### Отрицательные / Риски
- Нужно развернуть Kafka — новый компонент инфраструктуры, требует экспертизы
- Команда АБС должна реализовать Kafka Consumer для чтения заявок
- Небольшая задержка между подачей заявки и появлением её в АБС (асинхронность)
- Требуется документация новых API для дальнейшего расширения

### Нейтральные
- Интернет-банк на текущей версии ASP.NET MVC 4.5 не интегрируется с Kafka напрямую — это ограничение учтено в архитектуре (ИБ → REST → Deposit Application Service → Kafka → АБС)
- На этапе MVP бэк-офис продолжает обрабатывать заявки вручную через АБС; полная автоматизация — следующий этап
