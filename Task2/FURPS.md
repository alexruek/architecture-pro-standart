# FURPS+ — Требования для проекта цифровой трансформации банка Стандарт

> Контекст: MVP — онлайн-подача заявки на депозит (сайт + интернет-банк) и онлайн-заявка на кредит.

---

## F — Functionality (Функциональность)

| ID | Требование | Источник | Арх. значимо | Комментарий |
|----|-----------|---------|:------------:|-------------|
| F1 | Клиент может подать заявку на депозит на сайте, указав ФИО и номер телефона | Описание задания | Да | Новый канал взаимодействия; требует интеграции сайта с системой КЦ |
| F2 | После подачи заявки на сайте менеджер КЦ связывается с клиентом и может предложить особые условия | Описание задания | Нет | Операционный процесс; системная интеграция сайт -> КЦ |
| F3 | Клиент в интернет-банке видит список депозитов с актуальными ставками и персонализированными предложениями | Описание задания | Да | Требует единого хранилища ставок вместо XLS-файлов; данные из АБС |
| F4 | Клиент подтверждает заявку на открытие депозита в интернет-банке через СМС-код | Описание задания | Да | Функционал СМС-подтверждения реализуется командой банка, а не подрядчиком |
| F5 | Клиент видит предодобренное предложение по кредиту в интернет-банке и может подать быструю заявку | Описание задания | Да | Требует интеграции интернет-банка с кредитным конвейером и скорингом |
| F6 | Клиент может подать заявку на кредит с сайта (новый клиент, данные только в БКИ) | Описание задания | Да | Скоринг без внутренних данных АБС; только через БКИ API |
| F7 | Сотрудники бэк-офиса депозитов и кредитов имеют доступ к единой системе управления ставками | Описание задания | Да | Замена Excel-файлов; необходимо определить систему-источник ставок (АБС или отдельный сервис) |
| F8 | При обращении клиента в отделение депозит открывается без участия бэк-офиса (целевое состояние — год) | Описание задания | Да | Автоматизация процесса; фронт-офис работает только через АБС |
| F9 | Кредитная заявка, начатая клиентом онлайн (сайт или ИБ), должна продолжаться сотрудником отделения в АБС без повторного ввода данных | Описание задания | Да | Требует сквозного идентификатора заявки, пробрасываемого из онлайн-канала в АБС через кредитный конвейер; ключевое архитектурное требование к интеграции каналов |

## U — Usability (Удобство использования)

| ID | Требование | Источник | Арх. значимо | Комментарий                                                                  |
|----|-----------|---------|:------------:|------------------------------------------------------------------------------|
| U1 | Процесс открытия депозита онлайн не должен занимать более 10 минут для клиента | Собственное | Нет | Сейчас в отделении 20 мин — 1 час; онлайн должно быть быстрее                |
| U2 | Интерфейс подачи заявки на депозит доступен без авторизации на сайте | Описание задания | Нет | Новые клиенты заходят на сайт без учетной записи                             |
| U3 | В интернет-банке клиент сразу видит, одобрена ли заявка на кредит (статус в реальном времени) | Описание задания | Да | Влияет на архитектуру: нужен синхронный или near-realtime ответ от конвейера |

## R — Reliability (Надежность)

| ID | Требование | Источник | Арх. значимо | Комментарий |
|----|-----------|---------|:------------:|-------------|
| R1 | Интернет-банк и сайт должны быть доступны 24/7, допустимый простой не более 0.1% в месяц (99.9% SLA) | Собственное | Да | Уже есть резервный ЦОД; необходимо настроить автоматическое переключение. Цифра взята из типовых требований к розничным банковским каналам — при необходимости подлежит согласованию с бизнесом |
| R2 | При сбое СМС-шлюза заявка на депозит не теряется; клиент получает уведомление о повторной отправке | Собственное | Да | Требует механизма retry и хранения состояния заявки |
| R3 | Данные о кредитных заявках не теряются при сбое передачи из АБС в кредитный конвейер | Описание задания | Да | Сейчас передача раз в сутки через БД; нужна проверка целостности |

## P — Performance (Производительность)

| ID | Требование | Источник | Арх. значимо | Комментарий |
|----|-----------|---------|:------------:|-------------|
| P1 | Решение по кредитной заявке должно быть готово в течение 1 рабочего дня | Описание задания | Да | Сейчас цикл до недели; ограничивающее звено — передача данных раз в сутки |
| P2 | Ответ скоринговой системы на запрос от кредитного конвейера должен быть приемлемым для пользовательского сценария; для сценариев с достаточными данными — в пределах рабочего дня | Собственное | Да | Исходное требование "не более 30 секунд" снято как необоснованная инженерная гипотеза. Конкретный SLA скоринга должен быть согласован с командой скоринга отдельно |
| P3 | Страница со ставками по депозитам в интернет-банке загружается не более 2 секунд | Собственное | Нет | Стандартное веб-требование; кэширование ставок на уровне приложения |

## S — Supportability (Поддерживаемость)

| ID | Требование                                                                                             | Источник | Арх. значимо | Комментарий |
|----|--------------------------------------------------------------------------------------------------------|---------|:------------:|-------------|
| S1 | Ставки по депозитам должны обновляться ежедневно без участия IT-команды                                | Описание задания | Да | Требует UI или API для управления ставками силами бэк-офиса |
| S2 | Функционал СМС-подтверждения должен быть реализован и поддерживаться командой банка без подрядчика     | Описание задания | Да | Сейчас СМС-функционал в ядре системы подрядчика; нужно вынести в сторону банка |
| S3 | Система кол-центра должна быть расширяема для добавления новых скриптов звонков партнерским КЦ         | Описание задания | Нет | Платформа подрядчика поддерживает расширение; команда банка может вносить изменения |
| S4 | Интернет-банк должен допускать самостоятельные изменения командой банка без обновления ядра подрядчика | Описание задания | Да | Монолит на ASP.NET MVC 4.5; обновление ядра только через подрядчика |

## R — Restrictions (Ограничения)

| ID | Ограничение                                                                                                                                                  | Тип | Арх. значимо | Комментарий |
|----|--------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|:------------:|-------------|
| C1 | Интернет-банк работает на ASP.NET MVC 4.5 / .NET Framework 4.5 / MS SQL                                                                                      | Технологическое | Да | Обновление ядра только через подрядчика; ограничивает выбор технологий для новых модулей |
| C2 | АБС написана на Delphi + Oracle / PL-SQL, логика сосредоточена в процедурах БД; текущий основной способ интеграции — прямой доступ к БД или вызов PL-SQL API | Технологическое | Да | Это ограничение текущего состояния, а не абсолютный закон архитектуры. Новые решения могут использовать иные способы интеграции при наличии соответствующей экспертизы и согласования с командой АБС |
| C3 | Система КЦ — платформа подрядчика (Java Spring Boot, React, PostgreSQL)                                                                                      | Технологическое | Нет | Банк может вносить изменения в обработчики самостоятельно |
| C4 | Новые клиенты обязаны пройти личную идентификацию в отделении (регуляторное требование)                                                                      | Бизнес / Регуляторное | Да | Онлайн-заявка на депозит/кредит с сайта — только первый шаг; финализация в отделении |
| C5 | Данные, передаваемые с сайта, содержат персональные данные и должны шифроваться (HTTPS/TLS)                                                                  | Безопасность | Да | Явно указано в описании задания |
| C6 | Сотрудники бэк-офиса депозитов и кредитов не должны иметь доступа к данным друг друга                                                                        | Безопасность | Да | Явно указано в описании процесса открытия депозита |
| C7 | Кредитный конвейер получает данные из АБС раз в сутки через репликацию БД                                                                                    | Интеграционное | Да | Ограничивает скорость обработки кредитных заявок; требует пересмотра для онлайн-заявок |
| C8 | Система скоринга не может быть дополнительно нагружена массовыми предрасчетами предодобренных предложений в рабочие часы                                     | Технологическое | Да | Явно указано в описании кредитного направления; определяет архитектуру Pre-Approval Batch: ночной процесс на основе кэша скоринга, без новых вызовов скоринга в течение дня |
